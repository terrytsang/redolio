# REDO v1.6 — Positioning Intelligence & Hero Engine: repository audit and gap matrix

Source: `REDO_Upgrade_PRD_v1.6_Positioning_Intelligence_Hero_Engine.json` (backward-compatible extension of v1.5).
Audited against the repository at the start of the v1.6 work. Status values follow the PRD: **existing**, **partial**, **missing**, **conflicting**.

## What the repository already provides (reused, not rewritten)

| Capability | Where | v1.6 use |
|---|---|---|
| Crawl + evidence | `SiteCrawler`, `EvidenceBuilder`, `evidence_items` (`evidence_key`, excerpt, page) | The evidence ledger's source material |
| Website DNA | `WebsiteDna.dna_json`: offerings, audience, value proposition, trust signals, CTAs; claims carry `evidence_ids` + `confidence`; `observed_facts` vs `inferences` vs `uncertainties` | Seed for the positioning profile |
| Model layer | `MetaModelClient` + `AbstractModelClient` (generic `callStage`, per-stage instructions + `StageSchemas`) | New stages = interface method + instruction + schema; no client rewrite |
| Validation pattern | `App\Services\MetaApi\Validation\*` (authoritative, deterministic) | Same pattern for hero gates |
| Blueprint engine (v1.5) | registry, 6 hero variants, `DesignSpecV15` (`design_spec_json['v15']`), `ContentMappingService` | Hero copy flows through the existing mapper; new data is additive (`['v16']`) |
| Real-browser QA | `scripts/visual-qa/*`, `BrowserService` | Extended with a hero measurement script |
| SSRF/untrusted content | `SsrfGuard`, egress proxy, `ContentValidator` | Unchanged; hero fields reuse `ContentValidator` safe-string rules |

| v1.6 requirement | Status | Finding | Plan |
|---|---|---|---|
| Positioning profile before hero copy (HERO-AC-001) | missing | Nothing builds a category/audience/benefit/proof profile | `PositioningProfile` + `PositioningIntelligenceService` |
| Evidence statuses (verified / user-confirmed / inferred / unknown / contradicted) (AC-003) | partial | DNA separates facts from inferences but has no status taxonomy, no user confirmation, no contradiction handling | `PositioningEvidence` ledger; status is **computed by code** (grounding check), never trusted from the model |
| Contradiction handling (AC-018, TEST-03) | missing | Conflicting founding years / counts across pages are not detected | Deterministic cross-page comparison; disputed claims excluded from copy |
| User correction / confirmation (HERO-WF-01) | missing | Only DNA editing exists | PATCH positioning: confirm / edit / reject / resolve |
| Diagnose existing hero (AC-004) | partial | `diagnosis` stage reports site issues generally; no hero checks | `HeroMessagingDiagnosisService`: the 10 PRD checks, deterministic, traceable to evidence |

| Hard factual gates in code (AC-002, AC-006, TEST-06/07) | conflicting | Today only an ad-hoc `keepOriginalPositioning` guard exists; unsupported numbers/superlatives/credentials in the hero are not rejected | `HeroCopyValidationService`; the old guard stays for legacy flow only |

## Additive migration plan (no destructive change)

New tables only; no existing column or row is altered:
`positioning_profiles`, `positioning_evidence`, `hero_copy_options`, `hero_copy_approvals`, `hero_render_validations`, plus `hero_generations`
(async job status for polling; not in the PRD data model, required by its "return job IDs" rule).
`design_specs.design_spec_json` gains an optional `v16` key. Historical specs are never rewritten: approving hero copy creates a **new spec version**.

## Verified facts / assumptions

* Meta Models API: Responses API with flat `text.format` JSON schema is already verified in this repo (`docs/meta-api-verified.md`); new stages use the same generic path.
* The project already has image input only where the provider supports it; v1.6 needs none (measurement is DOM-based).
* Browserless font-readiness/DOM-measurement support is **not verified** (no account). Hero measurement runs on the local provider; on any other provider the result is `unavailable`, never `pass`.
